## 二、角色权限矩阵（重构后）

### 2.1 三角色定位（参考行业最佳实践）

> **背景调研**：参考 Xroad（QuantBox）、天勤量化、Reluna、TradingAgents-CN 等平台的角色权限设计，VIEWER 角色在业内对应"只读监控者"的职能，而非具体的"用户类型"。一个 VIEWER 账户背后可能是一位风控经理、一位合规审计师、一位 LP 投资人，或一位投资委员会成员——他们的共同特征是"需要看，但不能动"。

#### 角色全景对照表（借鉴行业实践）

| StockQuant 角色 | Xroad 对应 | 天勤量化对应 | Reluna 对应 | TradingAgents-CN 对应 | 核心定位 |
|----------------|-----------|------------|------------|---------------------|---------|
| `VIEWER` | View only / Risk manager / Back office | 临时授权审计人员 | Client / Compliance / Risk Manager | （无） | 只读监控者 |
| `TRADER` | Trader / Support | 机构操作员 | Trader / Head of Investment | user | 交易执行者 |
| `ADMIN` | Administrator | 机构管理员 | Global / Admin | admin | 平台管理员 |

#### 三角色精确定义

| 角色 | 角色名（中文） | 核心权限 | 适用人群（典型用户画像） | 不能做什么 |
|------|--------------|---------|-----------------------|-----------|
| `VIEWER` | **只读观察者** | 查看所有市场数据、策略、回测结果、投资组合、AI 分析、审计日志（仅自己）+ **提交回测/优化做策略验证** | 1. **机构风控经理** — 监控交易风险敞口<br>2. **合规审计师** — 审查交易合规性<br>3. **LP 投资人/投资委员会** — 查看基金表现<br>4. **策略研究员** — 浏览/回测验证策略<br>5. **监管观察员** — 监测异常交易行为 | ❌ 下单/撤单<br>❌ 创建/修改/删除策略<br>❌ 修改任何系统配置<br>❌ 管理用户 |
| `TRADER` | **交易员（用户级）** | VIEWER 全部权限 + 策略创建/修改/删除 + 交易下单/撤单 + 策略部署 | 1. **机构交易员** — 执行买卖指令<br>2. **量化研究员** — 编写/回测/优化/部署策略<br>3. **基金经理** — 管理投资组合、调仓<br>4. **个人量化爱好者** — 全功能使用平台 | ❌ 修改系统设置<br>❌ 启停调度器<br>❌ 清空 AI 记忆/缓存<br>❌ 查看全局审计日志<br>❌ 管理用户 |
| `ADMIN` | **平台管理员** | TRADER 全部权限 + 系统配置 + 用户管理 + AI 基础设施运维 + 全局审计 | 1. **平台运维工程师** — 维护系统运行<br>2. **IT 管理员** — 管理用户账号/权限<br>3. **技术负责人** — 调整 AI 模型/管线配置<br>4. **DevOps/SRE** — 监控调度器、清理缓存 | （理论上无限制）<br>但应遵循"最小权限原则"——日常运维用 TRADER 账户，仅在需要管理时切换到 ADMIN |

#### 关键设计决策（基于行业调研）

1. **VIEWER 不是"低级用户"，而是"职能隔离角色"**
   - 借鉴 Xroad 的 `View only` + `Risk manager` + `Back office` 三种角色的共性
   - VIEWER 账户的持有者往往是机构内的高决策权人员（风控总监、合规官、LP），他们需要看到一切，**可以提交回测做策略验证**，但不应误操作影响实盘交易
   - 因此菜单设计上：VIEWER 能看到所有数据展示页面 + 参数优化（回测验证需要），但所有影响实盘交易的按钮（下单/撤单、策略部署、交易启停）一律隐藏或禁用

2. **TRADER 是"用户级"的核心，对应机构主力用户**
   - 借鉴天勤量化的"机构操作员" + Xroad 的 `Trader` + Reluna 的 `Trader/Portfolio Manager`
   - 涵盖交易执行、策略研发、回测优化、组合管理——量化投研交易全流程
   - 不拥有系统级权限，保证交易操作与系统管理职能分离（参考天勤"三权分立"原则）

3. **ADMIN 专注于"平台治理"，不应承担日常交易职能**
   - 借鉴 Xroad 的 `Administrator` + Reluna 的 `Global/Admin` + TradingAgents-CN 的 `admin`
   - 拥有用户管理、系统配置、AI 基础设施运维、全局审计四大职能
   - 独立"系统管理"菜单分组，与业务菜单视觉隔离，避免误操作

4. **角色徽标颜色（基于行业惯例）**
   - `ADMIN` = **红色** (`red`) — 警示色，提示高权限账户
   - `TRADER` = **蓝色** (`blue`) — 主业务色，平台主力用户
   - `VIEWER` = **灰色** (`default`) — 中性色，只读观察者

```typescript
export function usePermission() {
  const { user } = useAuthStore()
  const roles = getUserRoles(user)
  return {
    isAdmin: roles.includes('ADMIN'),
    isTrader: roles.includes('TRADER') || roles.includes('ADMIN'),
    isViewer: roles.includes('VIEWER'),
    can: (requiredRoles: string[]) => requiredRoles.some(r => roles.includes(r)),
    canWrite: roles.includes('TRADER') || roles.includes('ADMIN'),
    canManage: roles.includes('ADMIN'),
  }
}
```

```typescript
// 包裹 antd Button，根据角色自动 disabled 或隐藏
export function PermissionButton({ requiredRoles, mode = 'disable', ...props }) {
  const { can } = usePermission()
  if (!can(requiredRoles)) {
    if (mode === 'hide') return null
    return <Tooltip title="无权限"><Button {...props} disabled /></Tooltip>
  }
  return <Button {...props} />
}
```

## 四、假设与决策

### 4.1 假设
- PostgreSQL 数据库已在 `localhost:54321` 运行（沿用 .env 中 `DATABASE_URL`）
- 前端开发服务器默认 `localhost:5173`
- 后端 OpenAPI 文档在 `http://localhost:8000/openapi.json`
- 现有 `Repository` 类位于 `stockquant.persistence.repository_v2`，已支持 `get_user`/`save_user`

### 4.2 决策
- **菜单分组方案**：采用 antd `<Menu>` 的 `type="group"` 子组件渲染分组，避免 SubMenu 嵌套展开的交互成本
- **角色徽标颜色**：ADMIN=红色(`red`)、TRADER=蓝色(`blue`)、VIEWER=灰色(`default`)
- **VIEWER 菜单裁剪**：VIEWER 看不到"参数优化"和"交易"，因为这两个功能本质是写入操作
- **trading-demo 路由**：直接删除，不保留兼容重定向
- **后端路由冲突修复**：`chat_complete` 改为 `/api/ai/strategy/chat`，`chat_stream` 改为 `/api/ai/strategy/chat-stream`，可能与前端现有调用不兼容，需要在前端同步更新调用路径
- **用户管理不实现复杂权限矩阵**：用户只能被分配单一主角色（roles 数组虽然支持多个，但 UI 上简化为单选），保持 MVP 简洁

### 4.3 不在本次范围
- 不做 SSO/OAuth 集成
- 不做细粒度 RBAC（如按策略 ID 授权）
- 不重构各业务页面内部布局（仅做按钮级权限）
- 不重写自动生成的 API 客户端（`web/src/generated/`）
